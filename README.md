# CRM-LID1.1 · Лиды

Модуль **Leads** платформы AI-First Business OS — вход воронки CRM: приём лида из канала → квалификация (скоринг) → распределение на менеджера → конвертация в сделку (Lead Qualifier & Router, ФАЗА 1). Здесь же UI-прототип воронки лидов (`index.html`).

## Границы репозитория

**Здесь живёт всё про лиды:**
- модель `Lead` (своя схема БД `leads.*`), статусы new → qualified → routed → converted;
- движок `leads.py`: детерминированный скоринг (без AI), выбор воронки (новые/постоянные/тендер/проект), распределение по правилам (география, продукт, нагрузка);
- API `/leads`: приём, список, квалификация, распределение, конвертация;
- AI-обоснование квалификации (`ai.py`) — Итерация 1, за feature-flag, поверх детерминированного балла;
- обработчики событий: «кампания → лиды», обратная связь «сделка создана → ссылка у лида»;
- `index.html` — UI-прототип канбана лидов (5 стадий, BYN).

**Здесь НЕ живут (отдельные репозитории):**
- **CRM-блоки** — сделки, доска, карточка, документы/1С, Price Engine, сообщения → репозиторий `CRM`;
- **Тендеры** — своя воронка → отдельный репозиторий.

## Возможности (циклы 1-16 + харденинг)

Поверх базового приёма/квалификации/распределения наросли рабочие тактики отдела лидорубов:
- **Скоринг и SLA** — авто-балл на входе, скорость первой реакции РАБОЧИМИ часами (9-18, вс — выходной);
- **Экспресс-передача** и конвейер «Разобрать целевых» (`express-bulk`) — квалификация+раздача одним действием;
- **Умная маршрутизация** — к лучшему закрывающему по конверсии с поправкой на загрузку; ключевые лиды (🔑) — без штрафа;
- **План/факт лидоруба** (`/plan`) — дневная норма и темп; **скорборд передач** продавцам (Σ КП, зависшие >24ч);
- **Качество источников/UTM** (`/stats/sources`) — какие каналы дают целевых и деньги;
- **КП на лиде** (`/items`, каталог-пикер) — переносится в сделку при конвертации; в событие идёт `counterparty_id` эталона;
- **Резолв клиентов через MDM** — обращение действующего клиента не выглядит холодным; память об отказе (`revived_from_id`);
- **Пост-передача под контролем** — возраст «у продавца», просрочка следующего шага, сторож «сделка не создана»;
- **Недозвон/повтор** (`/attempt`) — попытки+перезвон в очереди, «↑ повтор» поднимает вернувшегося клиента;
- **Рецикл «не сейчас»** — отсрочка 30/90/180 дн с авто-возвратом (wake-on-read), без фантомных дублей;
- **Безопасность** — роуты под `require_permission` (read/write/route); вложения: пред-гард размера, удаление, том для файлов;
- **Живая доска** — поллинг приёма + минутный тик SLA-чипов; видимые ошибки действий; валидация границ приёма.

## Интеграция через шину событий (§2.4/§2.5)

Модуль не импортирует другие модули; все связи — событиями:
- `marketing.campaign.launched` → приём лидов из кампании;
- `leads.lead.converted` → модуль sales (репозиторий `CRM`) создаёт сделку;
- `sales.deal.created` (с `lead_id`/`deal_id`) → лид получает ссылку `deal_id`.

Поэтому конвертация здесь **не создаёт сделку напрямую** — это главное отличие после выноса из CRM.

## Структура

Код — содержимое модуля `modules/leads/` монорепо (импортирует `core.*`); сам по себе не запускается, подключается к ядру через `ModuleContract` (`module.py`). Подключён как git submodule суперпроекта `CMR-ERP_main`; миграции лежат в общей цепочке Alembic суперпроекта (`migrations/versions/*lead*`, актуальный head — 0101).

## Правило коммитов

Любой функционал лидов коммитим сюда. CRM-блоки и тендеры — только в их репозиториях; здесь допустимы лишь точки интеграции через события шины.
